# AGENTS.md

This file provides guidance to Agents when working with code in this repository.

## What this project is

A Gradle plugin (`ee.schimke.composeai.preview`) plus supporting tools that discover `@Preview` composables in compiled Kotlin classes and render them to PNG outside Android Studio. Targets both Jetpack Compose (Android, via Robolectric) and Compose Multiplatform Desktop (via `ImageComposeScene`).

## Common commands

**The full toolchain builds and runs in the agent cloud environment** — not just unit/functional tests but the end-to-end Android/Robolectric and Desktop catalog renders (`composePreviewRenderAll`, `compose-preview` CLI, the `design-catalog-*` `bundle pack` + `compose/figma-svg` export, and the `FigmaFidelity` render-vs-SVG scoring). Nothing here is CI-only: build it, run it, and measure it in-session rather than deferring to the `design-artifacts` / preview-comment workflows. The first `./gradlew` invocation resolves the toolchain + dependencies through the agent proxy, so it is slow; subsequent builds are warm. See [`agent-cloud.md`](https://github.com/yschimke/skills/blob/main/skills/compose-preview/references/agent-cloud.md) for the network allowlist and the `install.sh --android-sdk` setup step.

**Compose Desktop previews render headlessly here — no `DISPLAY`, X server, or `xvfb` needed.** The desktop backend rasterizes through Skia's software path (`skiko-awt-runtime-linux-x64` + `ImageComposeScene` drawing offscreen), so `./gradlew :samples:cmp:composePreviewRenderAll` produces PNGs/GIFs on a bare headless Linux container. Verified end-to-end in-session (BUILD SUCCESSFUL, 36 rendered artifacts under `samples/cmp/build/compose-previews/renders/`). If a desktop render ever *looks* broken in a sandbox, it's almost never the windowing system — check these two load-bearing details first:
- **The render subprocess must run on the JDK 17 toolchain.** Gradle resolves it from the `toolchainVersion=17` pin in [gradle/gradle-daemon-jvm.properties](../gradle/gradle-daemon-jvm.properties). The cloud container already ships a JDK 17 (`/opt/jdk17`) that Gradle's "Common Linux Locations" auto-detection finds, even though the container's default `java` on `PATH` is JDK 21 — so no manual JDK install is needed for the render itself (Android/Robolectric SDK 36 is the separate case that wants JDK 21+; see [RENDERER_COMPATIBILITY.md](RENDERER_COMPATIBILITY.md)). A stale daemon left over from a JDK-21 launcher can poison toolchain detection (`Cannot find a Java installation … {languageVersion=17}`) — `./gradlew --stop` clears it.
- **The render JVM starts with package-store directories pruned from `LD_LIBRARY_PATH`** when it is not itself a Nix/Guix store JVM ([`RenderNativeEnv`](../gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/RenderNativeEnv.kt), applied to both the pooled worker and the per-capture fork). Store libraries carry the store's own glibc, so a hybrid sandbox — a store JDK running the daemon, a system JDK 21 picked by `jvmToolchain(21)` running the render — otherwise loses *every* preview to ``libc.so.6: version `GLIBC_ABI_DT_X86_64_PLT' not found`` (issue #3690). A store render JVM keeps everything it inherited, because `LD_LIBRARY_PATH` is the only channel its loader reads. Opt out with `-Dcomposeai.render.nativeEnv=inherit`; the failure mode and its diagnosis are in [DESKTOP_NATIVE_DEPS.md](DESKTOP_NATIVE_DEPS.md).
- **`java.awt.headless` is deliberately left unset on the render JVM.** Forcing `headless=true` breaks Skiko's font/graphics init; the plugin only sets the macOS-scoped `apple.awt.UIElement` (Dock/focus suppression) and relies on Skiko's own offscreen path on Linux. See the comment block in [RenderPreviewsTask.kt](../gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/RenderPreviewsTask.kt) (`invokeRenderer`). Don't add `-Djava.awt.headless=true` "to make it work in the cloud" — it does the opposite.

## Architecture

Four-stage pipeline, spread across the modules:

1. **Discovery** — [gradle-plugin/](gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/) scans compiled `.class` files with ClassGraph for `@Preview` annotations (including transitive multi-preview meta-annotations with cycle detection) and writes `build/compose-previews/previews.json`. Entry point: [DiscoverPreviewsTask.kt](gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/DiscoverPreviewsTask.kt).

2. **Task wiring** — [ComposePreviewPlugin.kt](gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/ComposePreviewPlugin.kt) registers `composePreviewDiscover`, `composePreviewRender`, and the user-facing `composePreviewRenderAll` aggregate. It detects Android vs CMP Desktop at configuration time and takes different paths:

   > **Config-only plugin / shared DSL.** The `composePreview { }` DSL types (`PreviewExtension`, `DaemonExtension`) and the `composePreviewApplied` marker task live in the separate `:gradle-plugin-config` included-build module (artifact `ee.schimke.composeai:compose-preview-config`, plugin id `ee.schimke.composeai.preview.config`). That module's `ComposePreviewConfigPlugin` is **configuration-only**: it contributes the DSL + marker but registers no render/discovery tasks, pulls in no AGP/renderer, and does **not** enforce the Gradle-version floor — so a consumer can commit `composePreview { … }` configuration without pinning the rendering runtime, and the `compose-preview` CLI auto-injects the full runtime plugin (`:gradle-plugin`) at its own version when it actually drives a render. The runtime plugin `api`-depends on `:gradle-plugin-config` and reuses its extension/marker via the create-or-find helpers in [`ComposePreviewDsl`](gradle-plugin/gradle-plugin-config/src/main/kotlin/ee/schimke/composeai/plugin/ComposePreviewDsl.kt), so both plugins coexist in one build with no double-registration. `:gradle-plugin-config` is the one artifact that must stay binary-stable across versions (it's resolved at a single conflict-resolved version when the consumer-pinned config plugin and the CLI-injected runtime meet on the buildscript classpath).

   - **Android:** uses AGP `artifactView` filters (`artifactType=jar`, `android-classes`) to resolve AAR-extracted class jars, copies JVM args from AGP's `test<Variant>UnitTest` task, and launches a Gradle `Test` task that runs [RobolectricRenderTest.kt](renderers/android/src/main/kotlin/ee/schimke/composeai/renderer/RobolectricRenderTest.kt) inside a Robolectric sandbox with `graphicsMode=NATIVE`. `android.jar` is added so the Robolectric runner classes load before the sandbox classloader takes over.
   - **Desktop/JVM:** creates a `composePreviewRenderer` configuration pointing at `:renderer-desktop`, then launches [DesktopRendererMain.kt](renderers/desktop/src/main/kotlin/ee/schimke/composeai/renderer/DesktopRendererMain.kt) as a subprocess with the module's runtime classpath plus the renderer.

3. **Rendering** — both backends reflect the target composable function, invoke it inside a background fill, and capture to PNG.

   - **Desktop:** `ImageComposeScene` at 2x density; two `scene.render()` calls so `LaunchedEffect`s / animations get one frame to settle before encoding.
   - **Android:** `createAndroidComposeRule<ComponentActivity>()` + `onRoot().captureRoboImage(...)`. Single always-on path: `mainClock.autoAdvance = false`, `advanceTimeBy(CAPTURE_ADVANCE_MS)`, then capture. The paused clock is what lets infinite animations (indeterminate `CircularProgressIndicator`, `rememberInfiniteTransition`, hand-rolled `withFrameNanos` loops) terminate deterministically instead of hanging Compose's idling resource. Time is expressed in ms rather than frame count so a future `@RoboComposePreviewOptions` / `ManualClockOptions(advanceTimeMillis = …)` override plugs straight in. `LocalInspectionMode = false` so animations actually tick. **a11y is daemon-only** — the standalone `composePreviewRender` Test task does not run ATF and does not write accessibility sidecars. The daemon (`:daemon:android`'s `RenderEngine`) is the single producer of a11y data products; consumers reach it through the VS Code chip toggle (per-preview `data/subscribe`), `compose-preview a11y` (spins up a temporary daemon), or the MCP server. Findings never fail a render — a11y is a data producer, not a gate. There is no DSL or Gradle property toggle anymore. The single-producer model — and the two distinct senses of "data product" (the daemon's structured JSON vs. the render manifest's secondary rendered artefacts, `RenderPreviewArtifact`) — is written up in [docs/DATA_PRODUCTS.md](DATA_PRODUCTS.md).
   
   Options are applied by hand in `renderDefault` rather than through `RoborazziComposeOptions` (its `configured(...)` chain wants an `ActivityScenario` it owns, awkward to share with `ComposeTestRule`): size/locale/uiMode/round/orientation via `RuntimeEnvironment.setQualifiers` (strict grammar order — locale, width, height, round, orientation, night); fontScale via `RuntimeEnvironment.setFontScale` (Configuration field, not a qualifier — same knob Roborazzi's `RoborazziComposeFontScaleOption` uses); background and inspection via `CompositionLocalProvider`.
   
   Capture path: `ShadowPixelCopy` is routed to `HardwareRenderingScreenshot` → `ImageReader + HardwareRenderer.syncAndDraw` via `robolectric.pixelCopyRenderMode=hardware` on the `composePreviewRender` `Test` task — the only path that replays Compose's `RenderNode`s correctly under Robolectric.

   **Coil-backed images (issue #2952).** A preview using coil's `AsyncImage` used to capture as a solid block with the artwork *and* its sibling content missing — an unresolved `AsyncImagePainter` reports **no intrinsic size**, so under `ContentScale.FillWidth` it swells to the parent's full height and shoves everything else out of frame. Two independent causes, both now fixed:
   - **coil never started the load.** `rememberAsyncImagePainter` copies `LocalInspectionMode.current` onto the painter and short-circuits to the request's *placeholder* when it's set — and the AS-parity default above is `true`. coil 3 makes that branch overridable via `LocalAsyncImagePreviewHandler`, so the renderer supplies a handler that runs the real request. coil 2 has no such hook, so [`ShadowAsyncImagePainter`](../renderers/android/src/main/kotlin/ee/schimke/composeai/renderer/ShadowAsyncImagePainter.kt) forces its `isPreview` field off — surgical, unlike flipping `LocalInspectionMode` globally, which would move every consumer branch onto its production path. The shadow needs `instrumentedPackages=coil.compose` (generated `robolectric.properties` for the Gradle path; `SandboxHoldingRunner` for the daemon) — **both halves are load-bearing, dropping either silently reverts to blank captures.**
   - **nothing finished the load.** coil fetches/decodes on `Dispatchers.IO`, which neither the paused `mainClock` nor Robolectric's looper drives. [`CoilPreviewSupport`](../renderers/android/src/main/kotlin/ee/schimke/composeai/renderer/CoilPreviewSupport.kt) swaps the **singleton** `ImageLoader` for one derived from the consumer's own (`newBuilder()`, so their components and caches survive) with every dispatcher rebound to `Dispatchers.Main.immediate`, so `execute()` runs inline inside the same `onRemembered` that started it. Install points: `RobolectricRenderTest.renderDefault` and `:daemon:android`'s `RenderEngine`, both immediately before `setContent`.

   **The wall clock (issue #3239).** Renders pin it, so a screen that paints the time produces the same PNG every run instead of diffing every minute. Robolectric's `SystemClock` is already deterministic under `LooperMode.PAUSED`, but `System.currentTimeMillis()` is only rewritten to it inside *instrumented* classes, so a consumer's own code and every library otherwise read the host's clock. Two halves, both load-bearing, same shape as the coil pair above: [`ShadowWearTimeSource`](../renderers/android/src/main/kotlin/ee/schimke/composeai/renderer/ShadowWearTimeSource.kt) replaces `androidx.wear.compose.materialcore.ResourcesKt.currentTimeMillis` — the single function both Wear Material and Material3 `TimeText` read the clock through, neither of which has an inspection-mode branch — returning [`PreviewClock`](../renderers/android/src/main/kotlin/ee/schimke/composeai/renderer/PreviewClock.kt)'s instant (default `10:10`, the literal `:samples:wear`'s `FixedPreviewTimeSource` and the Wear/Remote catalogs already paint); and `instrumentedPackages` names that same target, as a *class*, since Robolectric prefix-matches. Registered in the generated `robolectric.properties` and in `SandboxHoldingRunner`; drop either half and Wear clocks silently go back to drifting. **Shadow, not `SystemClock.setCurrentTimeMillis`** — moving the emulated clock would ignore any instant earlier than its current one, make every already-scheduled delayed message overdue via a 54-year jump (including work a consumer `Application.onCreate` posted under `useConsumerApplication = true`, which runs before the test method), leave `uptimeMillis()` reporting 54 years, and impose an ordering contract that breaks whenever a lane early-returns (the daemon's scroll and `figma-svg-long` modes do). A value-returning shadow has none of that, and is also what lets `fixedTime=off` genuinely mean "host wall clock" rather than "the emulated epoch". It matters most for `kind=ACTIVITY` / `kind=APP_TOUR`, where the app's own screen is the subject and there is no `@Preview` argument to inject a fixed `TimeSource` through; `:samples:wear`'s `WearAppSystemClockPreview` is the committed fixture that makes a regression visible in the diff bot. What it can't reach: `java.` is on Robolectric's do-not-acquire list, so `Calendar.getInstance()` / `java.time.*.now()` still read the host clock from inside the JDK — and the Desktop lane has no Robolectric at all, so the knob is Android-only and deliberately not forwarded there. Configure with `composePreview.fixedTime` / `-PcomposePreview.fixedTime=09:41` / `-Dcomposeai.render.fixedTime=off`.

   Both coil majors are `compileOnly` and reached through `Class.forName` behind a marker-class probe, so the common no-coil consumer loads none of it. **Remote (`http(s)://`) models are deliberately not fetched** — running coil inline puts the fetch under Android's main-thread network guard, and a preview whose pixels depend on live egress isn't reproducible (same reasoning as the warmed downloadable-font cache). Those requests are recorded by `CoilLoadDiagnostics` into `<png>.warnings.json` alongside the font fallbacks, so a blank image is diagnosable rather than mysterious. Escape hatch: `-Dcomposeai.coil.previewLoader=false` (covers the shadow too). Fixture + end-to-end assertions live in `:samples:android` (`AsyncImagePreviews.kt` / `AsyncImagePixelTest`).

`renders/` is ephemeral: rewritten every run, stale files deleted. Filenames are normalized — see [docs/RENDER_FILENAMES.md](RENDER_FILENAMES.md).

The CLI ([cli/](cli/src/main/kotlin/ee/schimke/composeai/cli/)) and VS Code extension ([vscode-extension/](vscode-extension/src/)) are thin drivers over the Gradle tasks — they shell out via the Tooling API (`GradleConnector.kt`, `gradleService.ts`) and read the resulting `previews.json` / PNG files. The CLI also ships a `compose-preview` binary with `installDist` for use as an agent/MCP backend.

## State seams

Coordination state for the edit→render→subscribe loop lives in a handful of named, unit-tested classes rather than module-level `Map`/`Set`/AbortController fields. **When you need to add to this loop, extend the existing seam rather than introducing a parallel mutable.**

VS Code extension (`vscode-extension/src/`):

- **`RefreshQueue`** ([refreshQueue.ts](../vscode-extension/src/refreshQueue.ts)) — save-driven refresh coalescing FSM. Owns `inFlight` / `pendingTarget` / `debounceElapsed` / `seenFiles`. Single entry point `dispatchSave(target, opts)` for both editor saves and file-watcher events. Tests inject a fake clock; real production uses `defaultRefreshQueueEffects`.
- **`EditorScope`** ([editorScope.ts](../vscode-extension/src/editorScope.ts)) — the `(file, module)` pair the panel is pinned to. Comparison is by `modulePath`, never reference identity. Don't add a parallel "what file is shown" tracker.
- **`PreviewModuleIndex`** (same file) — `previewId → owning module` lookup, with `replaceModule(module, freshIds)` for the "purge stale entries then install fresh ones" pattern. Per-preview action handlers (chip toggles, focus inspector, history) route through this.
- **`DaemonScheduler`** ([daemon/daemonScheduler.ts](../vscode-extension/src/daemon/daemonScheduler.ts)) — owns per-module subscription state (`subscribedPairs`) and exposes `setDataProductSubscription` which returns the `a11yTransition` verdict. The extension doesn't keep its own a11y subscription mirror.
- **`PreviewOverrideStore`** ([daemon/previewOverrideStore.ts](../vscode-extension/src/daemon/previewOverrideStore.ts)) — the host-authoritative per-preview overrides (permissions, Remote Compose named values, clear-background), plus the last-attached `compose/remotecompose` payload used to seed a first edit. Replaces four parallel `Map`/`Set`s keyed by the same `previewId`. **Every explicit edit handler dispatches `store.compose(previewId)`, not just the field it changed** — the daemon reverts any authoritative override a render omits, so sending one field drops the others. The first-edit seeding rule (seed from the snapshot once, never re-seed) lives in `applyRemoteComposeChange`; don't re-implement it at a call site.
- **`DaemonRefreshIndicator`** ([daemonRefreshIndicator.ts](../vscode-extension/src/daemonRefreshIndicator.ts)) — the top progress strip for the daemon save path. Replaces the `daemonRefreshActive` / `Label` / `Pct` / `Tick` / `Safety` quintet. Effects (posting, timers) are injected so the crawl and the safety ceiling are unit-testable without a webview. Note `armSafety()` is deliberately separate from `begin()`: the compile phase before a render is unbounded, and arming the ceiling early flashes the bar to done mid-compile.

Daemon (`daemon/core/src/main/kotlin/ee/schimke/composeai/daemon/`):

- **`SubscriptionStore`** ([SubscriptionStore.kt](../daemon/core/src/main/kotlin/ee/schimke/composeai/daemon/SubscriptionStore.kt)) — sticky `(previewId, kind)` bookkeeping. Three teardown methods (`unsubscribe`, `retainVisible`, `removeKinds`) return the dropped pairs so the caller routes `onUnsubscribe` through the right producer surface (`publicDataProducts` vs `activeDataProducts`).
- **`DeferredDiscoveryQueue`** ([DeferredDiscoveryQueue.kt](../daemon/core/src/main/kotlin/ee/schimke/composeai/daemon/DeferredDiscoveryQueue.kt)) — paths waiting for the post-render discovery cascade plus the watchdog that drains them if no render arrives. Watchdog scheduler is injectable; tests use a manual scheduler so race outcomes are deterministic.
- **`DataProductRegistry.renderModeFor(kind)`** ([DataProductRegistry.kt](../daemon/core/src/main/kotlin/ee/schimke/composeai/daemon/DataProductRegistry.kt)) — producers declare which kinds need a renderer mode tag (`"a11y"`, etc.). The dispatcher iterates subscribed kinds and asks the registry; **do not pattern-match on the kind string in `JsonRpcServer`**.

The seams are deliberately split per concern; a new feature usually maps to extending exactly one. If your change wants to add a new module-level `Map<String, …>` to `extension.ts` or `JsonRpcServer.kt`, check whether one of these classes already owns the conceptual state first.

## Git conventions

- **Git history must never attribute work to an AI agent — non-negotiable.** Commits are attributed solely to the human committer. Banned: (1) a `Co-authored-by:` trailer naming an agent (Claude / Codex / ChatGPT / Copilot / Gemini) or using an agent email, and (2) committing with an **author/committer identity that is an agent** — an `@anthropic.com` / `@openai.com` email, or an agent **name** (Claude, Codex, …). GitHub App bot accounts (`…[bot]`, e.g. `claude[bot]`) are exempt: they only land on branches and never reach the squash-authored `main`. Fine and left untouched: links to an agent session (`claude.ai/code`), the "🤖 Generated with …" and **`_Generated by [Claude Code]_`** PR/commit footers, and ordinary PR comments — they don't claim authorship, and the footer is useful, so keep it. PRs are squash-merged from the **PR title + body**, so a `Co-authored-by:` line in the PR description reaches `main` even when the commits are clean; scrub the description too. Enforced by the local [`.githooks/commit-msg`](../.githooks/commit-msg) hook and the [`No Agent Attribution`](../.github/workflows/no-agent-attribution.yml) CI gate — keep the shared `AGENT_NAME` / `AGENT_EMAIL` definitions in sync between them. Real human co-authors and `dependabot`/`renovate`/`github-actions` bot trailers are fine — the gate targets AI coding agents only.
- **Branch names are always `agent/…`, never `claude/…`** (or any other agent prefix — `copilot/…`, `codex/…`, `cursor/…`). Don't ask which prefix to use; it's always `agent/`. Rename a `claude/…` branch to `agent/…` before pushing. House style, pinned in [`claude.yml`](../.github/workflows/claude.yml) via `branch_prefix: agent/`, and sibling repos' CI (meshcore-mobile) hard-reject agent-named prefixes.
- **Use conventional commits for PR titles and commit subjects** (`fix:`, `feat:`, `docs:`, `test:`, etc.) so squash merges feed release-please correctly.
- **Before adding commits to an existing PR branch, check whether the PR has already landed.** Fetch `origin` and inspect the PR state or compare `origin/main` first. If the PR is merged, start a fresh branch from `origin/main` for follow-up work instead of stacking new commits onto the merged branch.
- **Run the formatter before committing.** CI's `format` job runs `./gradlew ktfmtCheckAll` and it's a hard gate — `ktfmtCheck` aborts on the first unformatted file. Before each commit that touches `*.kt`/`*.kts`, run `./gradlew ktfmtFormat` (or `./gradlew :<module>:ktfmtFormatMain :<module>:ktfmtFormatTest` for the touched modules) and stage the result. For VS Code extension TypeScript changes, run `npm --prefix vscode-extension run format`. Don't push without re-running these — the fix-up round-trip costs more than running the formatter locally.

## PR workflow

These rules also live in [CLAUDE.md](../CLAUDE.md#pr-workflow-must-follow); detail and rationale below.

- **Open PRs automatically.** When a coding task is finished, committed, and pushed, open a PR against `main` without prompting. Conventional-commit title, short summary, test-plan checklist — same shape as the `gh pr create` heredoc template the harness ships with. Skip this only when the user explicitly said "no PR" or framed the task as pure exploration. Always check first whether the branch already has an open PR (`list_pull_requests` or `search_pull_requests` filtered by head); if so, push to it instead of opening a duplicate.
- **Visual evidence means embedded, viewable images — not descriptions.** A UI-affecting PR (Compose `@Preview` output, the VS Code webview, overlays, wireframes, themes, icons, fixtures) must carry before/after evidence in the body as **actual rendered images embedded inline** — markdown `![](…)` pointing at the committed render PNGs (the commit-pinned `raw.githubusercontent.com/.../renders/<module>/<Preview>.png` URLs the diff bot uses) or images uploaded into the body. Describing what an image shows, or deferring to the diff-bot auto-comment, is **not** evidence — a reviewer must see the pixels without clicking through or re-running. If a surface genuinely can't be captured here, say so and embed a renderable proxy (e.g. the `compose/semantics-wireframe` SVG) or state how a human/CI verifies it. Text-only is correct only for non-visual changes.
- **Never wrap a link destination in backticks.** ``![alt](`url`)`` — and its cousin with the closing run pushed past the `)` — renders as literal text plus a stray code span, so the image never appears and a PR that did the expensive part right fails its own evidence bar over two stray characters. Write `![alt](url)`. The [`PR Body Syntax`](../.github/workflows/pr-body-syntax.yml) workflow repairs the description automatically when this slips through (repair + tests in [`.github/scripts/fix-pr-body-markdown.mjs`](../.github/scripts/fix-pr-body-markdown.mjs)). It rewrites the body **in place** on `opened` / `edited` / `reopened` / `synchronize`, so a description you just posted may change under you — that is the repair, not a reviewer edit, and re-posting the broken form will simply be repaired again. It only ever strips backticks touching a link destination; code spans and fenced blocks are left alone. Treat it as a safety net, not a licence to skip proofreading the body.
- **Subscribe to every PR you open.** Call `subscribe_pr_activity` for the PR's number on the same turn you open it. Don't ask the user whether to track — tracking is the default. Mention it in the reply so the user knows the session is now listening (e.g. "Opened PR #N and subscribed to its activity").
- **Respond to PR review comments and CI events automatically.** `<github-webhook-activity>` events on tracked PRs are not no-ops. For each event:
  - If the requested change is clear, in-scope, and not architecturally significant — push the fix, update the status checklist on the PR, and don't narrate each round in chat.
  - If the comment is ambiguous or touches something significant — use `AskUserQuestion` with enough context that the user can answer without scrolling back.
  - For CI failures on a PR the user asked you to babysit — re-diagnose and re-kick (rebase, re-run, push fix) until green. After several rounds with no progress, reply with the diagnosis and where you're stuck instead of going silent.
  - When everything is green, reply with the green status. That IS the deliverable.
- **Stop on request.** "Stop watching", "unsubscribe", "leave it alone" — call `unsubscribe_pr_activity` for that PR and stop pushing.
- **Don't auto-merge.** Opening, tracking, and fix-up commits are automatic; merging is the user's call. Don't enable auto-merge unless the user explicitly asks.
- **Regenerate the delivery branches after each merged change set.** `design-artifacts.yml` renders the catalogs and publishes the importable bundles to `design-artifacts/<system>` (appended on top of the branch tip, so each regeneration is a diffable commit — see [Delivery-branch history](design/DESIGN_CATALOGS.md#delivery-branch-history)); those branches go stale the moment a catalog (`samples/design-catalog-*`), the renderer, or the export driver changes. After such a change merges to `main`, dispatch the workflow (`actions_run_trigger` → `run_workflow` on `design-artifacts.yml`, ref `main`) and confirm the run succeeded, so the published stickers don't lag `main`.

## VS Code panel UI changes

Edits under `vscode-extension/src/webview/` or `vscode-extension/media/preview*.css` need a visual record. Capture a baseline + post-change PNG via the preview-harness and send both to the user before reporting the task done — the harness boots the real `<preview-app>` bundle headlessly against fixture JSON and is the panel's equivalent of a Compose `@Preview`. Loop and fixture authoring are documented in [`vscode-extension/preview-harness/README.md`](../vscode-extension/preview-harness/README.md#agent-workflow); seed fixtures are `grid-default` (multi-card grid) and `a11y-findings` (focus mode + Accessibility bundle). Use it for shape, layout, and theming — not as a substitute for `npm test` / `test:electron`, which still own behavioural correctness.

## Important constraints

- **No hardcoded special-case logic for extensions in the renderer / daemon / protocol layers.** Per-feature wiring like `if (spec.wallpaper != null) wrap(...)` or `inbound["material3Theme"]?.let { ... }` is a smell. The renderer drives extensions through metadata: a `PreviewOverrideExtension` (a `DataExtension<PreviewOverrides>`) registered in `PreviewOverrideExtensions` is what decides whether and how to wrap a preview, based on the merged `PreviewOverrides` bag. Adding a new override-driven feature lives entirely inside its connector module (`data/<feature>/connector/`) plus a `DaemonMain` registration line — `RenderEngine`, `JsonRpcServer.encodeRenderPayload`, and `PreviewManifestRouter` should not need to grow new branches. Same rule applies to data-product registries: don't sprinkle `if (kind == "compose/foo")` checks across the dispatcher; surface kinds via `DataProductRegistry.capabilities` and route through `CompositeDataProductRegistry`. **CLI canned reports follow the same rule**: implement `ExtensionReportRenderer` (per-extension load / annotate / print / threshold), register in `builtInExtensionReporters()`, and either bind it to a named command via `ReportCommand` (`A11yCommand` is the example) or leave it discoverable via `compose-preview extensions list` + `--with-extension <id>`. **Profiles (`compose-preview profile <path.json>`) are a thin args-synthesiser over `ReportCommand`** — captured flag combinations, not a programming model; richer user-defined behaviour is tracked as Kotlin scripting in [issue #1084](https://github.com/yschimke/compose-ai-tools/issues/1084) and should NOT be added by extending the profile schema. The CLI used to hard-code a11y-shaped fields into the base `Command` class; that's been factored out — don't reintroduce it.
- **File/IO goes through Okio, not `java.io.File` / `readText()` / `writeText()`.** All non-Gradle production code funnels disk access through [`:common-io`](../common/io) — `SystemFileSystem` (an Okio `FileSystem`) plus Okio's own blocking `read { … }` / `write { … }` / `source` / `sink`. Paths are `okio.Path` (`"x".toPath()`, `dir / "file"`). **Inject the `FileSystem`, don't hardcode the global.** Code that touches files takes an Okio `FileSystem` rather than naming `SystemFileSystem` at the call site: stateless functions / `object`s take a defaulted `fileSystem: FileSystem = SystemFileSystem` parameter, and stateful classes take a `private val fileSystem: FileSystem = SystemFileSystem` constructor parameter. Production behaviour is unchanged (the default is the real filesystem); tests inject a `FakeFileSystem` (the `okio-fakefilesystem` test artifact) and exercise IO in memory. Only the composition roots (`main` entry points) legitimately name `SystemFileSystem` directly. `:common-io` is **deliberately coroutines-free**: it has to stay loadable on the **render subprocess classpath** without dragging a `kotlinx-coroutines` version skew onto it (a skew there breaks Compose rendering with `NoSuchMethodError` — see [docs/RENDERER_COMPATIBILITY.md](RENDERER_COMPATIBILITY.md)). There is intentionally **no `suspend` / `Dispatchers.IO` layer** — `:common-io` is synchronous; the rare caller that wants to keep blocking IO off a UI thread does its own `withContext` / `runBlocking` at the call site (e.g. `:bundle-viewer`'s bundle load runs in a Compose `LaunchedEffect`). Reach for `java.io.File` only at a **hard third-party boundary** that demands it — the Gradle Tooling API (`GradleConnector.forProjectDirectory`, the serialized `PreviewModule` — `okio.Path` isn't `Serializable`), `java.util.zip.ZipFile` (or use `FileSystem.openZip`), `URLClassLoader` (`file:` URLs), `ImageIO` (bridge via `source().inputStream()` / `sink().outputStream()`), `RandomAccessFile`, `ProcessBuilder` — and bridge there with `Path.toFile()` / `file.path.toPath()`, keeping the `File` local to that call. **Exempt** (stay `java.io.File` / `java.nio`): the Gradle plugin + `build-logic` (Gradle's own world), the CodeQL-recognized `java.nio.Path` zip-slip containment checks, the BTA in-process compiler's `java.nio.Path` source list, and the `java.nio.Path`-native, `ATOMIC_MOVE`-based history stores (`LocalFsHistorySource` / `GitRefHistorySource`).
- **Isolated Projects is deliberately NOT enabled** ([gradle.properties](gradle.properties) carries `org.gradle.configuration-cache.problems=fail` but no `org.gradle.unsafe.isolated-projects=true`). IP is *incompatible* with the compose-preview CLI / MCP / VS Code workflow: those drive Gradle through the auto-injected init script ([AutoInject.kt](../cli/src/main/kotlin/ee/schimke/composeai/cli/AutoInject.kt), [initScript.ts](../vscode-extension/src/initScript.ts)), which applies the plugin via `allprojects { buildscript { … } }` — a cross-project configuration IP rejects (`Project ':' cannot access 'Project.buildscript' … via 'allprojects'`). There is no IP-safe init-script mechanism that puts an AGP-aware plugin on every project's buildscript classloader (init-classpath loading would, but lands the plugin on a sibling classloader to AGP → `NoClassDefFoundError`; PR #1483). The full investigation — every injection mechanism tried under IP, the exact failures, and the upstream Gradle change that would actually fix it — is written up in [isolated-projects-autoinject.md](isolated-projects-autoinject.md). The Tooling API daemon honours whatever a project's gradle.properties sets, so enabling IP — here OR in a consumer's build — breaks every tooling-driven run, not just CI. **Don't re-enable it globally.** The plugin and the init script *warn* when they detect IP active (`ComposePreviewPlugin.warnIfIsolatedProjectsEnabled` via the `BuildFeatures` service; the init script's `settingsEvaluated` probe), so a re-enable is loud rather than silent.
  - **Plugin code is still kept IP-clean, and that's the gate.** The configuration cache is on and strict (`problems=fail`), so the same discipline applies regardless: resolve classpaths/JVM args at configuration time via lazy providers — never call `.files` inside a task action or touch `project.*` at execution time; no `allprojects {}` / `subprojects {}`, no `project(":other")`, no `gradle.taskGraph.whenReady { allTasks }`; shared per-project setup goes in a `build-logic` convention plugin applied per-module. IP-cleanliness is verified per-invocation by the functional tests that *self-enable* `org.gradle.unsafe.isolated-projects=true` in their synthetic projects ([AppliedMarkerFunctionalTest](../gradle-plugin/src/functionalTest/kotlin/ee/schimke/composeai/plugin/AppliedMarkerFunctionalTest.kt), [CrossProjectMetadataFunctionalTest](../gradle-plugin/src/functionalTest/kotlin/ee/schimke/composeai/plugin/CrossProjectMetadataFunctionalTest.kt)) — keep adding to those when changing discovery / task wiring so the manual-apply path stays IP-safe.
  - **Every module must apply `composeai.base-conventions`** in its `plugins {}` block — this is what brings ktfmt (`googleStyle`) and the history-gate test system property that the old root `allprojects {}` block used to provide build-wide. A new module that omits it won't be formatted or covered by the `ktfmtCheckAll` gate. (The root project is the one exception: a build-logic plugin on the root classpath leaks to every subproject and collides with their versioned plugin aliases, so the root carries no ktfmt — keep root `build.gradle.kts` / `settings.gradle.kts` formatted by hand.) `ktfmtCheckAll` / `ktfmtFormatAll` discover the module set via a path list `settings.gradle.kts` hands to the root build through a system property.
  - **The two `functionalTestWith*` e2e aggregates need a two-phase invocation** (`./gradlew :cli:installDist :gradle-plugin:publishToMavenLocal` first, then the e2e task) — the configuration cache can't express the old cross-build "functionalTest mustRunAfter installDist" ordering. CI already does this; mirror it locally.
- **CMP Desktop previews require `implementation(compose.components.uiToolingPreview)`** — the bundled `@Preview` has `SOURCE` retention and is invisible to ClassGraph otherwise.
- **CMP Desktop renders need skiko's four native deps reachable *from the render JVM's loader*** (`libGL.so.1`, `libX11.so.6`, `libfontconfig.so.1`, `libstdc++.so.6`). When one isn't, every preview in the module fails with `UnsatisfiedLinkError: …/libskiko-linux-x64.so: libGL.so.1: cannot open shared object file`. Two traps make this worse than a missing package: a **Nix/Guix-store JDK** is patchelf'd to a loader that ignores `/etc/ld.so.cache` and `/usr/lib`, so `ldd` and `ldconfig -p` (which run the *system* loader) both say the library is fine while the render fails; and `LD_LIBRARY_PATH` only counts when it's **exported** into the environment the Gradle daemon and its render subprocess inherit — `echo $LD_LIBRARY_PATH` will happily print an unexported shell variable that never reaches them (`env | grep ^LD_LIBRARY_PATH=` is the check that matters), and a daemon started before the export keeps its old environment until `./gradlew --stop`. `compose-preview doctor` emits `env.desktop-natives` on any project with a CMP module and resolves each soname the way the render JVM would; the full write-up is [docs/DESKTOP_NATIVE_DEPS.md](DESKTOP_NATIVE_DEPS.md). Note that a failed render leaves `.error.json` sidecars that count as task outputs, so `composePreviewRender` goes UP-TO-DATE and re-reports the stale failure — verify a fix with `--rerun`, not a plain re-invocation.
- **Toolchain:** Java 17, Kotlin 2.3.20, Gradle 9.4.1+, AGP 9.1.1, CMP 1.11.1. Always use the bundled `./gradlew` wrapper. Don't loosen the toolchain to a newer JDK to avoid the install — AGP 9.1.0 / Robolectric still target 17, and bumping silently produces classes-vs-resources skew on the consumer's unit-test classpath.
- **Bringing up a fresh sandbox.** Run [`scripts/install.sh --android-sdk`](../scripts/install.sh) — it installs JDK 17 (when `./gradlew` fails with "Unable to download toolchain") and the Android `cmdline-tools` + platforms 36 and 37.0 + build-tools (when an Android sample fails with "SDK location not found"). Pass `--jdk 17,21` to install multiple JDK majors in one go. `ANDROID_HOME` defaults to `/opt/android-sdk` on cloud sandboxes (root or `CLAUDE_CLOUD=1`), `$HOME/Library/Android/sdk` on macOS, and `$HOME/Android/Sdk` elsewhere; `local.properties` lands as `sdk.dir=<that path>` (gitignored; CI uses `ANDROID_HOME` instead). Cold end-to-end run takes ~3 min. Two things that bit a fresh web session hard enough to be worth stating (issue #3695): the platform package for `compileSdk = 37` is **`platforms;android-37.0`**, not `android-37` — the latter doesn't exist and fails the whole `sdkmanager` invocation it appears in, taking the 36 packages down with it; and the JDK step deliberately does **not** re-provision a JDK the box already has. It looks for one under `/usr/lib/jvm/` and `/opt/jdk<major>` — where [`scripts/setup-cloud-jdk.sh`](../scripts/setup-cloud-jdk.sh) puts Temurin via the SessionStart hook — before touching `apt-get`, and if apt can't supply one it warns and continues rather than aborting the Android SDK work, which doesn't depend on the daemon toolchain at all. Consumer-facing cloud Setup-script recipe in [skills/compose-preview/references/agent-cloud.md](https://github.com/yschimke/skills/blob/main/skills/compose-preview/references/agent-cloud.md#custom-mode-android-consumers).
- **Robolectric native-runtime extraction is shared.** Native graphics needs about 200 MB of native libraries, fonts, hyphenation data, and ICU data. Robolectric normally extracts a fresh `robolectric-nativeruntime*` copy for every forked JVM; Gradle can terminate a worker before Robolectric's shutdown hook completes, so repeated renders or `:daemon:android:testDebugUnitTest` runs used to fill `/tmp` (issue #3281). [`SharedNativeRuntimeLoader`](../renderers/android/src/main/java/ee/schimke/composeai/renderer/SharedNativeRuntimeLoader.java) replaces that loader through Robolectric's service interface. It initializes one immutable cache per Robolectric version × Android SDK × OS/architecture under `$XDG_CACHE_HOME/composeai/robolectric-native` (else `~/.cache/composeai/robolectric-native`), guarded by an inter-process file lock and completion marker. Every render JVM shares the roughly 185 MB of fonts, ICU, and hyphenation data. Separate Robolectric sandbox classloaders require distinct native-library images for JNI registration, so each sandbox briefly copies only the roughly 10 MB library under `sandbox-libraries/`; Unix hosts unlink it immediately after loading and Windows removes it at normal JVM shutdown. A checkout from before this fix may still have old host-level directories; `du -sh /tmp/robolectric-nativeruntime*` identifies them when a misleading Kryo failure contains `No space left on device`.
- **Do not run `collectPreviewInfo` / other internal plugin tasks by hand** — the plugin wires them as dependencies of `composePreviewRenderAll`.
- **Plugin version** is driven by `.release-please-manifest.json` at the repo root (single source of truth, maintained by release-please). The three `build.gradle.kts` files read that manifest and compute next-patch `-SNAPSHOT` for local builds; CI overrides with the `PLUGIN_VERSION` env var from the git tag or `snapshot.yml`. See [docs/RELEASING.md](RELEASING.md).
- **Android renderer's Robolectric SDK tracks the consumer's `compileSdk`.** The gradle plugin reads `android.compileSdk` from each consumer module's `finalizeDsl` and writes the matching `sdk=N` line into the generated `robolectric.properties` (see [GenerateRobolectricPropertiesTask](../gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/GenerateRobolectricPropertiesTask.kt) + [AndroidPreviewSupport](../gradle-plugin/src/main/kotlin/ee/schimke/composeai/plugin/AndroidPreviewSupport.kt)). The previous hardcoded `sdk=35` triggered `PackageParser: Requires newer sdk version #36 (current version is #35)` on `compileSdk = 36` consumers (issue #1248). Consumers can override the auto-detected value with `composePreview.sdkVersion = N` for the rare case where they want a different framework level than `compileSdk`. Supported range is gated by the bundled Robolectric (currently `4.17-beta-2`, API 21–37, though the plugin's `MAX_SUPPORTED_SDK` clamp still tops out at 36); Robolectric SDK 36 additionally requires the test JVM to be JDK 21+ (`DefaultSdkProvider.verifySupportedSdk`), so consumers on `compileSdk = 36` need to be on a JDK 21 toolchain. Our own modules stay on JDK 17 + Robolectric SDK 35 (see `RobolectricHost.ANDROID_SDK` and the `@Config(sdk = [35])` annotations in `:daemon:android` / `:data-uiautomator-*` self-tests); bump those together with `robolectric` in [gradle/libs.versions.toml](../gradle/libs.versions.toml) and the project's toolchain. Capture depends on Robolectric's shadowed `ImageReader` / `PixelCopy` path, historically fragile across SDK × Robolectric combinations (e.g. `ShadowNativeImageReaderSurfaceImage.nativeCreatePlanes` is `maxSdk`-gated). Re-run `:samples:android:composePreviewRenderAll` end-to-end when bumping either the SDK ceiling or Robolectric.
- **The two cache layers are different, and `setup` alone only gets you the perishable one.** [`.github/actions/setup`](../.github/actions/setup/action.yml) wires `gradle/actions/setup-gradle`, which restores the whole Gradle *home* from the GitHub Actions cache — downloaded dependencies **and** `caches/build-cache-1`, the local build cache of task outputs. So a `setup`-only job is not literally starting from zero. What it has is a *point-in-time snapshot*: `setup-gradle` reports `Save was skipped` when it restores an exact key match, so the entry does not accumulate task outputs across runs, and the moment a change alters cache keys build-wide (a `build-logic` edit, a dependency bump) the snapshot stops matching anything and the job compiles from source — permanently, with nothing to repopulate it. The BuildFetch **remote** build cache is the durable layer that survives key churn, because a designated seeder keeps refilling it. It is opt-in per workflow via [`.github/actions/buildfetch-cache`](../.github/actions/buildfetch-cache/action.yml), called after `setup`. The failure mode is invisible — a job with only `setup` looks slow, not broken. `vscode-extension-e2e` shipped that way, and when a `build-logic` change invalidated the Actions-cached snapshot its five shards went 1m41s→8m32s (wear) and 5m48s→13m00s (cached-preload) with no remote layer to fall back on. **When adding a workflow that invokes Gradle, add both.** Deliberate exceptions, each for a reason that is not "we forgot": `codeql.yml` (the analysis database needs real compilation — a cached build produces nothing to analyse), `daemon-bench.yml` (a benchmark; a build cache changes what it measures), `release.yml` / `snapshot.yml` (publishing paths stay cache-conservative so a poisoned entry can't reach a released artifact), and `vscode-extension-e2e-external.yml` (it clones an external consumer and runs *its* Gradle build in the same job — `buildfetch-cache` exports the token through `$GITHUB_ENV`, so adding it would hand the repo's cache credential to third-party build code).
- **Many opportunistic writers, plus one that always finishes.** The local build cache is on **everywhere**, including on runs that push ([settings.gradle.kts](../settings.gradle.kts)). Gradle only pushes a task it actually *executes*, so a run contributes exactly what it had to build and nothing is paid twice. That makes pushing cheap enough for the big main-branch producers to all do it — `ci.yml`, `integration.yml` and `vscode-extension-e2e.yml` carry an `rw-token` gated on `github.event_name == 'push'` (PR-head code must never see a write token), and they stay `cancel-in-progress: true` because a superseded verification result is worthless and a cancelled run simply pushes less. [`gradle-cache-seed.yml`](../.github/workflows/gradle-cache-seed.yml) is the floor under that: the one writer that is never cancelled, in its own workflow because workflow-level `cancel-in-progress` kills the whole run and job-level concurrency can't rescue a job whose run was killed.
  - **This inverts an earlier design, deliberately.** The old rule was one exhaustive seeder, forced to execute everything by *disabling* its local cache. It doesn't work at this repo's merge rate: measured 2026-08-09, five commits landed in the 26 minutes between a seed (`69c0517`) and the next e2e run (`7677a3f2`) — one touching preview discovery, which rotates every render key — so the e2e run hit none of what the seed pushed. One writer that has to build from scratch to be useful cannot stay ahead of that; several that each push their own misses can. Don't reintroduce `local { isEnabled = !remotePushEnabled }`: on a CI runner the Actions-restored local cache is a frozen snapshot (`Save was skipped`), so disabling it buys a full cold build rather than the "warm cache suppresses pushes" it was guarding against.
  - `cancel-in-progress: true` is for disposable verification runs. Baseline and publishing workflows whose completed ordering is part of correctness (for example `compose-preview.yml` main-baseline production and releases) stay uncancelled; cancelling them leaves later consumers comparing against stale state.
- **Renderer-vs-consumer AndroidX version alignment is load-bearing.** The renderer AAR goes out of its way to avoid dragging newer Compose / Activity / Core versions onto the consumer's unit-test classpath (since AGP builds `apk-for-local-test.ap_` from the consumer's own deps, classes-vs-resources mismatches are easy to introduce). Known failure signatures, current mitigations (`compileOnly` + `extendsFrom(testConfig)` + `ui-test-manifest` injection), follow-ups for `compose-preview doctor`, and tile-rendering gaps are catalogued in [docs/RENDERER_COMPATIBILITY.md](RENDERER_COMPATIBILITY.md) — consult it before bumping `libs.versions.toml` or changing how `AndroidPreviewSupport` wires the test classpath.

## Tests

- `:gradle-plugin:test` — unit tests on preview-data / device-dimension parsing.
- `:gradle-plugin:functionalTest` — Gradle TestKit tests that apply the plugin to synthetic projects and assert on `previews.json` + rendered PNGs. These are the source of truth for end-to-end plugin behavior; add one here when changing discovery or task wiring.
- `:renderer-android:test` — JVM unit tests for render helpers (no Robolectric).
- `vscode-extension` uses Mocha against compiled `out/test/**`.
